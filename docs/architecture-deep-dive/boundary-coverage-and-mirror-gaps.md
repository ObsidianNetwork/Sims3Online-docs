# Boundary coverage and mirror gaps

Server authority defines who owns outcomes; boundary coverage defines how
much of those outcomes a client can present. A healthy server can complete
gameplay while a client remains visually stale or applies an incomplete
local representation. This page organizes common gap classes by the
mechanism involved so that a fix can be placed at the correct layer.

## Coverage layers

| Layer | What is missing when it fails | Example symptom |
|---|---|---|
| Input capture | Player intent never leaves local game | Menu pick appears to do nothing |
| Controller authorization | Valid intent is rejected or wrong intent accepted | Claim or identity error |
| Game execution | Server never starts requested work | Queue refusal or route failure |
| State extraction | Server state changes but no snapshot/event field reports it | Client UI remains stale |
| Identity resolution | Client cannot map a server actor/object to a local entity | Missing Sim, chair, book, or prop |
| Presentation recording | Engine operation is not captured | Correct server posture, wrong client animation |
| Replay policy | Record is translated into unsuitable local gameplay | Duplicate autonomy or rejected interaction |
| Local simulation | Client object/lot does not advance as needed | Terminal replay stalls |
| Late-join history | Active presentation state is not reconstructed | Stale animation or driver on join |

A symptom can cross more than one layer. Diagnose the first missing or
incorrect transition, not just the final visual result.

## Common mechanisms

### Insert-time validity

Many game interactions run a validity test at insertion time. A client
replayed interaction may fail even when the server already began it because
the client has a different posture, inventory, target object, or action
queue. Reconstructing the exact interaction is not always equivalent to
replaying the server's accepted decision. In the one-simulator model, the
safer default is to present server-originated state rather than locally
re-run gameplay logic.

### Posture and object prerequisites

Some interactions require an actor to be in a particular posture or a target
to be available before insertion. If the presentation path omits a precursor
operation or uses a local target that differs from the server target, the
client can reject the command or remain in an intermediate posture. A
“settle delay” may hide an ordering race but does not establish a correct
state transition.

### Routing and coordinates

A route request can be planned once while later position updates attempt to
move the actor elsewhere. The local route follower may continue toward its
original target. Replaying a semantic route or applying a final settled
position can be more reliable than injecting continuous teleports, but the
choice depends on what the stream actually records.

### Autonomy interference

The local game can choose its own action between mirror updates.
Equal-priority queue entries, autonomous director scheduling, or unfiltered
social target selection can produce a different client action. Suppression
must cover the relevant mechanism, not only the user-directed insertion
point.

### State-machine and callback behavior

A posture or animation is often backed by live state-machine objects and
callbacks rather than a serializable enum. Applying a label such as
“sitting” does not construct the full animation, event, or interaction
state. Some script events are generated by the clip itself and may have no
corresponding handler on a puppet.

### Object and Sim identity

A server process-local id may not resolve in the client. A client must have
an alias or supported creation path before applying a record. Props and
furniture may be generic visual copies, while Sim descriptions need their
own lifecycle transfer when absent from the local save.

### Lot activity

A visible Sim does not guarantee that the matching client-side lot objects
are ticking. A terminal interaction can fail to progress if its local object
script or state machine is not being simulated at the required fidelity.
This is separate from network interest and server authority.

## Triage matrix

| Symptom | First evidence to compare | Likely gap class |
|---|---|---|
| Action not visible on either side | Client intent, server response, server queue | Capture, authorization, execution |
| Server action finishes, client stays idle | Snapshot fields and client acknowledgement | State extraction or delivery |
| Client shows wrong Sim | Alias map and description identity | Sim identity |
| Client holds a prop after server drops it | Object alias and hand/slot reconciliation | Object lifecycle/presentation |
| Actor reaches wrong destination | Route record, target identity, final position | Route semantics |
| Client starts its own action | Local autonomy and gate status | Authority enforcement |
| Late join repeats old animation | Retained active state and stop/release events | History lifecycle |
| Menus disagree after social | Relationship state on server/client | Persistent state mirroring |

## Evidence discipline

A controller-level test can prove that a record is generated and decoded. It
cannot prove the live game has the expected posture or that a native route
completes. State each result with its evidence type: static code inspection,
managed test, offline harness, single-game probe, or multi-client live
scenario.

Record the baseline and the changed behavior. A live result should include
the game and integration version, save characteristics, actor/target
context, game speed, window state, and observation duration. Do not publish
private paths, personal data, unlicensed game assets, or raw local run
artifacts.

## Repair strategy

1. Reproduce the mismatch with a minimal scenario.
2. Compare authoritative server state and the client's applied state.
3. Locate the first transition absent or different in the client trace.
4. Determine whether the correct fix belongs in input, validation,
   extraction, identity, record, replay, or local gate.
5. Prefer a shared engine boundary or an authoritative state field over a
   one-interaction special case.
6. Add a controller test for the contract and a live test for the
   engine-facing claim.
7. Verify join, reconnect, and cleanup paths as well as the immediate
   action.

## Gap severity

| Severity | Meaning | Example response |
|---|---|---|
| Authority leak | Client can mutate shared gameplay independently | Block rollout; fix enforcement first |
| State divergence | Client's durable state differs from server | Repair extraction/application and resync |
| Missing entity | A required actor or target cannot be resolved | Fix identity/lifecycle or reject safely |
| Presentation mismatch | Server outcome is correct but local visual differs | Improve recorder/replay coverage |
| Cosmetic omission | Nonessential effect is absent | Document support limit and prioritize separately |

A visually obvious issue is not always the most severe. A small authority
leak can be more important than a large animation mismatch.

## How to verify / test

- Keep an authoritative server trace and client apply trace for the same
  interaction.
- Test accepted-then-failed and accepted-then-completed lifecycle cases.
- Include actors and objects created after the world loads.
- Test both live and late-join presentation for long-running actions.
- Verify no client-only actions enter shared state during mirror playback.
- Exercise snapshot repair after intentionally missing an update.
- Ensure unresolved objects are reported and do not silently map by numeric
  id.

## Cross-layer failure example: terminal interaction

A client can know that an actor should use an object but still fail because
the interaction's local insertion test requires an already-established
posture, the object id cannot be resolved, or the client lot does not tick
the relevant object. The server interaction may still be correct. The
correct repair may be to transfer state or present a recorded boundary
operation, not to invoke the same terminal interaction locally.

| Evidence | Likely explanation |
|---|---|
| Server and client queue both empty | Command was rejected, failed, or completed |
| Server queue active, client queue empty | Presenter model may intentionally omit gameplay queue; inspect UI mirror |
| Server and client queue active, posture differs | Posture/transition state missing or replay order wrong |
| Server object id absent client-side | Object alias/semantic matching required |
| Client object present but frozen | Lot simulation gate or local engine activity limitation |
| Animation differs after state agreement | Presentation seam or state-machine callback gap |

## Regression strategy

For each repaired gap, retain a regression at the correct layer: a pure
policy test for filtering, a codec test for identity fields, an authority
test for no client mutation, and a live scenario for the visible game
behavior. A known-failing test expectation should not be mistaken for
product acceptance; the result should say whether the behavior passed or was
merely recognized by the harness.

## Example: classify a missing book interaction

A server Sim reads a book, but a client sees the Sim standing idle. Capture
a trace at each boundary:

1. Confirm the server interaction started and the authoritative queue still
   reports it.
2. Confirm the server snapshot includes the actor and the book target.
3. Confirm the client's alias maps both identities to local entities.
4. Check whether a presentation record for the state machine and held-book
   attachment was emitted.
5. Check whether the record arrived before the client apply acknowledgement.
6. Verify that the client book object and local lot are active enough to
   present the operation.
7. Check whether late-join history represents the action as still active.

If the server queue completed but the client is missing a visual, this is a
presentation or history gap. If the server never started the interaction,
investigate command validation and game execution instead. The same symptom
has different fixes depending on the first divergent step.

## State repair versus visual repair

A full snapshot can repair state fields such as position or motive, but may
not reconstruct a live engine state-machine driver or an object attachment.
Conversely, replaying an animation can make the screen look right while the
client's persistent relationship or inventory remains stale. Define whether
a reported mismatch concerns durable state, transient interaction state, or
local presentation before selecting a repair.

| Repair method | Appropriate target | Risk if misapplied |
|---|---|---|
| Full snapshot | Stale mirrored state | Does not recreate all transient engine objects |
| Alias refresh | Wrong/missing local entity | Does not create missing description data by itself |
| Replay stream | Visual engine operation | Can duplicate or revive stale operations |
| Local state correction | Supported presentation field | May diverge again if server field is not updated |
| Re-run interaction | Generally not a presentation repair | Client can invent a competing outcome |

## How to verify / test

- Save a minimal reproducible scenario with the actor, target, and
  preconditions identified.
- Capture server and client records with timestamps and correlation where
  available.
- Label each check as state, lifecycle, identity, or presentation.
- Validate that a repair does not create local gameplay or mutate the server
  save unexpectedly.
- Repeat after late join and after a client disconnect/reconnect.
- Confirm the issue is reflected accurately on [status](../status.md) if it
  affects users.
