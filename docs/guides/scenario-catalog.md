# Scenario catalog

The checked-in `scenarios/` directory contains JSON-driven live scenarios. `scripts/scenarios.py` discovers their names and runs their steps against the local server/client game setup; these are not offline unit tests.

## Browse and run

```powershell
python scripts/scenarios.py list
python scripts/scenarios.py health
python scripts/scenarios.py run sit-dining
python scripts/scenarios.py history --last 5
python scripts/scenarios.py explain sit-dining --run latest
```

`run` accepts scenario names, repeat count, boot options, client count, watcher settings, environment overrides, rejoin mode, and soak controls. The exact options are in `python scripts/scenarios.py run --help`. Use `health` first: a broken host/client process makes subsequent scenarios blocked, not meaningful failures.

## Starter scenarios

Start a [first live multiplayer session](first-live-session.md) with one host and one mirror. Use a freshly loaded disposable save with the same household and starting area as the checked-in `scenarios/start/home.json`. The repository provides the scenario definitions and coordinates. Create or supply the compatible save locally.

| Case | Prepare in the test world | What the runner captures |
|---|---|---|
| `phone-standing` | The same household and claim, with a compatible smartphone in Jennifer's inventory that offers Browse the Web. | Jennifer's standing phone interaction, held prop, and motion evidence from both games. |
| `sit-dining` | Sims named Jennifer and Pablo, the client claim on Jennifer, and a reachable dining chair near the reset location. | Jennifer's route to the chair, seated state, and motion evidence from both games. |
| `shower` | A working shower within reach of Pablo, with a clear route to the bathroom and no occupancy or privacy conflict. | Pablo's route, shower animation and end state on the host and mirror. |
| `sleep-bed` | A reachable, usable bed near Pablo with a free side or slot. | Pablo's route to the bed and the sleeping presentation on both games. |

```powershell
python scripts/scenarios.py health
python scripts/scenarios.py run phone-standing sit-dining
python scripts/scenarios.py health
python scripts/scenarios.py run shower sleep-bed
```

Start the host with `SIMSONLINE_ROUTE_STREAM=1` as shown in the first-session guide. Run the two batches on the same stack so the second reset exercises the transition from seating to the next case. The runner executes selected files in catalog order within each batch. Check both `.omo/run/scenarios/<run>/report.md` files for the actual verdicts. In the JSON, `expect` describes the expected result for scoring. Use `python scripts/scenarios.py explain <case> --run <run>` for a failed or blocked case.

### Observed results on the development fixture

The [verified Windows session](first-live-session.md#verified-session) ran these cases without the optional local conversation probes: `phone-standing` passed with matching end-state checks, and with route streaming off `sit-dining` reached the seated state on both games before failing the motion verdict on a client-only placement jump and turn. With `SIMSONLINE_ROUTE_STREAM=1`, both games walked to the chair and the `sit-dining` motion check passed. Run `python scripts/scenarios.py run sit-dining` to reproduce the check and `python scripts/scenarios.py explain sit-dining --run latest` to inspect the events.

Two `shower` attempts recorded `CRASHED` during reset, before the host queued `TakeShower`. On an isolated `sleep-bed` attempt, the mirror crashed while Pablo was walking to the bed. An object-sound stop arrived in each crash window. A full dump from a later reproduction identified the failing call as the generic string dictionary generated by the legacy compiler for the sound opcode switch. Audio replay now dispatches those 14 case-sensitive opcodes through a guarded character switch. The earlier crash reports have native stacks, so the managed call was confirmed only in the full capture.

The latest cold run still recorded an interpreter access violation while the mirror applied the initial claim and presentation state, before the phone interaction. The replay batches in that window contained zero audio operations. The latest report lacks the managed heap needed to identify its calling method.

| Case | Observed result on the development fixture |
|---|---|
| `phone-standing` | Passed earlier. A later run crashed before the interaction. |
| `sit-dining` | Passed with route streaming enabled. The later crash blocked another repeat. |
| `shower` | Crashed during reset before `TakeShower` was queued. |
| `sleep-bed` | Blocked in the combined run. The separate run queued `BedSleep` and then crashed on the approach. |

If the client goes down during reset, the runner stops the current case before issuing its interaction and blocks subsequent cases while the stack stays down. Recheck `health` before starting another case if a bridge goes silent.

These cases ask the host to start the interaction and check the resulting presentation on the mirror. Use the [manual input check](../repo-reference/scenarios-catalog.md#manual-checks-for-input-and-game-time) to exercise client input capture separately.

The four definitions run without a maintainer-local probe. The shared reset also attempts to read conversation state with an optional local probe. A clean checkout can log `conversations … not read`. Start from a fresh save with both Sims idle and out of conversation to keep that optional check out of the acceptance path. Conversation and multi-client scenarios have their own additional prerequisites. Check both the `steps` and `after` lists for `scratch/` probe paths before running a different case.

## Result interpretation

- **Pass** means the configured assertions matched the evidence recorded for that run.
- **Fail** means at least one scenario check failed, including a step, assertion, motion watch, or server/client comparison; inspect `explain` and raw evidence before changing code.
- **Crashed** means a game went down during the case, including during reset. Check the recorded stage and crash report before attributing it to the interaction named by the case.
- **Blocked** means a prerequisite or host-health check prevented a meaningful scenario execution.
- **Rescore** re-evaluates saved motion evidence with current detectors; it does not rerun the game.

The runner also offers `status`, `wait`, `rescore`, `during`, `arms`, and `exposure` for saved-run inspection and controlled comparisons. Do not treat repeated runs on a changed world/save as identical inputs.

## Add a scenario safely

Keep scenario JSON focused on one observable behavior. Declare the required actors, setup, operations, waits, and explicit success conditions. Use a disposable save and a stable start state. A scenario that relies on an untracked maintainer-local probe must say so without implying that the probe ships in this repository.
